## 背景

扩展当前先创建内存端点缓存，然后在注册命令前等待 `scanWorkspace()` 完成。因此每次 Extension Host 重启都会执行全量扫描，并延迟所有命令。扫描期间，每个匹配的源文件都会被读取和解析，常规逐文件日志会同时写入两处；受监听文件只有在新解析结果非空时才会替换缓存。

搜索已经预计算了可搜索字段，但有界结果仍通过有序数组插入维护。`maxResults` 最大可达 1000，使该操作接近 `O(N*K)`。初始 QuickPick 还会为全部端点创建条目。Base URL 虽然缓存在内存中，但每次查询仍会重新发现资源目录并读取文件元数据，然后才能确认缓存命中。

用户明确接受 Extension Host 重启后重新全量扫描，因此不使用持久化端点或扫描状态。

## 目标与非目标

**目标：**

- 首次索引结束前即可使用命令。
- 索引期间可搜索当前已有结果，并明确展示索引状态。
- 文件变更采用完整、无陈旧数据的替换语义。
- 在不改变端点检测和排序契约的前提下，减少文件枚举、解析、日志、搜索和 Base URL 发现工作。
- 保持确定性结果顺序及现有配置行为。
- 通过回归测试和确定性大型缓存性能守卫证明行为。

**非目标：**

- 不将端点数据、扫描元数据、Base URL 数据或其他索引持久化到磁盘。
- 不新增继承端点、自定义组合注解、配置类路由或占位符解析。
- 不替换注解解析器，也不引入 Worker Thread。
- 不新增依赖或用户配置键。
- 后台索引新增端点时，不自动替换已经打开的 QuickPick 条目；用户输入始终查询实时缓存。

## 设计决策

### 1. 后台激活与显式扫描状态

扩展必须先创建服务并注册 watcher、订阅和命令，然后启动 `scanWorkspace()`，且 `activate()` 不等待其完成。`FileScanner` 暴露只读扫描状态和状态变更事件。`SearchUI` 在索引期间保持空 QuickPick 打开并设置 busy 状态；索引结束后清除 busy 状态，但不自动重排或替换可见条目。

这比首次搜索时才扫描更合适，因为可以保留预索引能力并让所有命令及时响应；也不必新增索引服务，因为 `FileScanner` 已经负责扫描串行化和进度。

后台失败在激活边界捕获并记录，避免未处理的 Promise rejection 进入 Extension Host。

### 2. 每次解析都完整替换文件缓存

`scanFile()` 在正常解析或快速判定无需解析后，都调用 `cache.updateFile(filePath, endpoints)`，即使 `endpoints` 为空。它返回端点数量，工作区扫描统计不再通过并发变化中的全局缓存大小推断单文件结果。

工作区扫描不再在 `scanFile()` 前重复查询和移除同一文件，避免重复过滤与克隆。watcher 变更和工作区扫描共用同一条替换路径。

### 3. 减少扫描候选与热点工作

多个字符串扫描模式组合为一个 brace-union include，只发起一次 `findFiles` 请求，并保留标准化去重作为安全边界。保守的注解预筛选只检查当前解析器已经支持的端点注解名称。未命中时写入空替换；误命中只会继续走正常解析。

Watcher 回调在安排防抖扫描前过滤命中排除 glob 的路径。内部小型 matcher 支持文档默认配置使用的语法：`*`、`**`、路径分隔符和 brace 选项，并进行独立测试。配置变更重建 watcher 时同时重建过滤条件。

移除或汇总常规逐文件扫描、状态记录和 watcher 日志，保留扫描开始、总量、完成、警告和失败信息，不增加新的日志配置。

合并 `findFiles` 优于并行执行多个模式，因为并行查询会放大文件系统遍历并仍需去重。解析器重写不在范围内，因为主要可避免成本来自解析不可能包含受支持端点的文件。

### 4. 保持稳定顺序的有界堆搜索

`EndpointCache.search()` 使用二叉堆维护不超过 `maxResults` 个候选，比较规则沿用现有分数比较器。每个候选保留原始缓存位置作为稳定的同分决胜条件。遍历结束后，再使用现有排序规则和稳定位置对保留结果排序一次。

候选维护复杂度由 `O(N*K)` 降为 `O(N log K)`，同时保持原有排名。全量排序会增加宽泛查询的内存用量；保留有序数组则无法解决本地测量中 `K=1000` 时的性能敏感问题。

### 5. 限制初始 QuickPick 分配

`SearchUI` 打开时读取一次已校验的 `maxResults`，初始条目和后续搜索统一使用该限制。索引进行中且缓存为空时，显示 busy 的空 QuickPick，而不是“无端点”警告；索引已结束且为空时保留现有警告行为。

用户若希望看到更多结果，可以提高现有配置，而不必默认承担为所有端点创建 UI 条目的成本。

### 6. 事件驱动失效的内存 Base URL 缓存

`BaseUrlResolver` 按标准化工作区路径缓存 Spring 配置发现与解析的最终结果。扩展为受支持的 `application*`、`bootstrap*` YAML/properties 文件创建 watcher。创建、修改和删除事件通过静态失效方法，仅清除所属工作区的缓存。

失效后，下次 URL/cURL 命令重新发现并解析配置。正常缓存命中不再遍历目录或读取元数据。缓存仅存在于当前进程，并在扩展停用或 reset 时清空。

事件失效优于重复签名检查，因为需要消除的成本正是重复发现。基于时间的缓存会允许任意时长的陈旧数据并周期性重复工作，因此不采用。

### 7. 并发与生命周期安全

扫描期间收到强制刷新请求时，不中断正在进行的文件系统操作，而是在当前扫描完成后排队执行新一轮全量扫描。缓存和扫描状态在新一轮开始前清理，使该轮读取最新配置，且旧扫描无法在清理后重新写入旧范围结果。文件读取或解析失败必须与“成功解析出零个端点”区分，失败文件不更新扫描状态，因此后续增量扫描仍会重试。

扩展停用会先将扫描器标记为已释放，阻止新的工作和 UI 更新，清理防抖及状态栏隐藏定时器，并等待已启动的后台扫描安全收束后再重置依赖单例。Base URL 的每个工作区维护内存版本号；异步解析开始时捕获版本，只在完成时版本未变化的情况下回填缓存。

配置重载任务与扫描任务都属于扩展生命周期：停用先设置终止标记并释放配置订阅，再等待已经进入异步阶段的配置重载和扫描收束。重载在每个异步边界后检查终止标记，不能在停用后重建 watcher。扫描队列若单轮失败但已经收到强制刷新请求，仍继续执行最新配置的全量刷新；没有排队刷新时才向调用方传播失败。状态栏隐藏定时器始终只有一个所有者，新一轮扫描会取消上一轮的隐藏计划。

## 风险与权衡

- **风险：搜索打开过早时只有少量或没有条目。** → 保持 QuickPick 打开并显示 busy，用户输入时查询实时缓存。
- **风险：注解预筛选误排除受支持语法。** → 根据受支持注解集合生成 token，并补充全限定名、Java、Kotlin 回归用例；误命中始终安全。
- **风险：自定义排除 glob 超出 matcher 支持范围。** → 仅编译文档约定语法，测试 Windows/POSIX 分隔符；无法安全编译时回退为不过滤。
- **风险：堆转换改变同分顺序。** → 保存缓存位置，并通过既有排序用例、同分稳定性测试和参考全量排序测试校验。
- **风险：配置 watcher 漏事件导致进程内 Base URL 陈旧。** → 同时监听创建、修改、删除；工作区和配置变更时主动失效，并保留测试和停用时的显式 reset。
- **权衡：不持久化意味着每次 Extension Host 重启仍会全量扫描。** → 这是已接受的设计；后台激活和减少扫描工作用于降低可感知启动成本。
